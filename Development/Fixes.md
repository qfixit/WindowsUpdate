1) (resolved) Start-Windows11Upgrade.ps1 (lines 86-89) invokes Invoke-PostUpgradeCleanup, but no such function exists in any loaded helper. On any run where Windows 11 is already detected (post-reboot validation or pre-existing Win11 device), this call will throw, drop into the catch path, and leave state/tasks/toast artifacts in place. Remediate by adding a cleanup helper (e.g., promote Connectwise RMM/PostUpgradeCleanup.ps1 into the main module set and dot-source it, or implement an Invoke-PostUpgradeCleanup function that removes reminder/runonce entries, clears C:\Temp\WindowsUpdate, and logs success) and ensure it’s loaded in Windows11Upgrade.ps1.

2) (resolved) ScheduledTasks.ps1 (lines 130-219) defines Register-PostRebootValidationTask twice with different behaviors (first registers an ONLOGON scheduled task to run PostUpgradeCleanup.ps1; second registers only a RunOnce to rerun Windows11Upgrade.ps1). The second wins, leaving the scheduled-task path dead code and making the intended post-reboot target ambiguous. This drift can produce mismatched cleanup behavior if the function order changes or when future edits assume the first definition is active. Remediate by keeping a single implementation that matches the documented RunOnce-only flow, deleting the stale version, and aligning the target (Windows11Upgrade vs PostUpgradeCleanup) with the desired post-reboot action.

3) (resolved) Start-Windows11Upgrade.ps1 (lines 64-82) sets $needsStaging/$pendingHandledViaSelfRepair based on a detected rebooted “ScriptRunning” state, but immediately resets those flags at  (lines 94-96). Any self-repair outcome from the earlier block is discarded, so the script can unnecessarily re-stage/download after a successful restage or misreport whether self-repair handled the pending state. Move the flag initialization above the self-repair check or guard the reassignments so they don’t overwrite a decision already made.

4) (resolved) Global $ErrorActionPreference = 'Stop' in Windows11Upgrade.ps1 (line 16) combined with Write-Log using Write-Error (MainFunctions.ps1:11-58) turns every error-level log into a terminating exception. Several catch blocks expect to log an error and continue cleanup (e.g., IsoDownload.ps1 (lines 32-35), Start-Windows11Upgrade.ps1 (lines 139-142)), but the log itself can short-circuit those steps, skipping failure markers or state resets. Remediate by making Write-Log emit errors with -ErrorAction Continue (or temporarily setting $ErrorActionPreference = 'Continue' inside the function), or by downgrading non-fatal diagnostics to WARN and reserving ERROR for cases where an exception is intended.

5) (resolved) SelfRepair.ps1 (lines ~49 and ~68) registers the post-reboot validation RunOnce twice inside the success path. This is redundant and can generate noisy log entries or unexpected LastRun times. Remediate by keeping a single registration call (e.g., after reboot reminder registration) or guarding the second call when the first succeeds.

6) (resolved) UpgradeConfig.ps1 Build-SetupArguments (lines ~80-88) always appends `/NoReboot` to the base arguments even though the default `SetupExeBaseArguments` already includes `/NoReboot`. This duplicates the switch and prevents base arguments from omitting `/NoReboot` if a future scenario needs setup to reboot itself. Remediate by only appending `/NoReboot` when it is absent from the base string or by removing it from the base template and letting the builder add it once.

Remediate by refactoring both to use the same shared cleanup helper and keeping a single source of truth for post-upgrade cleanup.

9) (new) Register-PostRebootValidationTask relies solely on an HKLM RunOnce entry that replays Windows11Upgrade.ps1 in the context of the first logged-on user (ScheduledTasks.ps1:130-160). On standard/non-admin logons, the post-reboot validation run will lack rights to delete tasks, RunOnce entries, or the staging folder, so cleanup can silently fail and keep RunOnce/reminder artifacts in place. Remediate by registering a SYSTEM-run scheduled task (logon or startup trigger) for post-reboot validation and using RunOnce only to kick that task off, or by explicitly running the validation script as SYSTEM (e.g., schtasks /run on a SYSTEM-owned task) instead of the interactive user context.
- This task should not run under the user context, and instead the system context. The entry script Windows11Upgrade.ps1 is invoked and ran as system to start.

10) (new) The BITS download loop has no timeout or progress-stall detection (IsoDownload.ps1:65-131). If a job sticks in TransientError/Suspended or stops transferring bytes, the while loop will sleep forever, leaving ScriptRunning.txt in place and never falling back to Invoke-WebRequest or marking a failure for self-repair. Remediate by tracking elapsed time/bytes transferred and canceling or restarting the job after a configurable inactivity window (e.g., 10-15 minutes) with a fallback to Invoke-WebRequest and a failure marker when all transports time out.
- Invike-WebRequest while run under the system context fails, and is slow to begin with. Hence the ust of BITS. Safeguard this with timed progress tracking (No progress in last 5 min) instead of setting an overall time that can differ depending on internet speed.

Remediate by delaying the stall timer until at least one progress sample is observed, resetting the timer on overall process CPU/disk activity, or extending the timeout with a safeguard that only trips when both progress and process I/O are idle.
